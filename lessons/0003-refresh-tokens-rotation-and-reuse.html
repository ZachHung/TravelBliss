Lesson 3 · about 30 minutes · API side

Staying signed in: refresh tokens, rotation and reuse

The access token dies after five minutes, yet you stay signed in for weeks. By the end of this lesson you will trace a refresh through the API line by line, and predict what happens when someone steals the refresh cookie.

Warm-up, from memory

1. To keep a token alive forever, someone decodes the payload, changes exp to the year 2100, re-encodes it, and keeps the old signature. What does the API do?
2. Where does a guarded field get the signed-in user from?

Part 1 · Why two tokens

From lesson 1: whoever holds a bearer token can use it. [RFC 6750 §1.2] If an access token leaks, it works for the thief until its exp. So TravelBliss keeps it short: five minutes (API_JWT_EXPIRED). But signing in every five minutes would be unbearable.

The fix is a second token with one narrow job. In OAuth's words, “refresh tokens are credentials used to obtain access tokens”, used “when the current access token becomes invalid or expires”, and, unlike access tokens, “never sent to resource servers.” [RFC 6749 §1.5]

Access token Refresh token
Lifetime 5 minutes 30 days idle (API_REFRESH_EXPIRED), at most 90 days from sign-in (API_SESSION_MAX_AGE); see Part 3
Signed with API_SECRET_JWT API_SECRET_REFRESH: a different secret
Kept by the browser in page memory an HttpOnly cookie, travelBliss_rf
Sent with every request, as Authorization: Bearer automatically with requests to the API; only refresh and sign-out read it
Also recorded in nowhere (until sign-out) Redis: refreshToken:<userId>:<token>
Two secrets mean the tokens cannot stand in for each other: verifying a refresh token with API_SECRET_JWT fails with invalid signature, exactly as in lesson 2.

Part 2 · Signing in with “Remember Me”

The sign-in form's Remember Me box becomes hasRefresh in the login mutation, then remember in SessionService.start: 

const { accessToken, refreshToken } = this.createTokens(userId);
if (remember) {
  await this.storeRefreshToken(userId, refreshToken, res);
}
return { accessToken };

Both tokens are always minted, but the refresh token only leaves the server when you tick the box. storeRefreshToken does two things:

  1. writes Redis key refreshToken:<userId>:<token>, set to expire at the token's own exp (EXAT exp): Redis forgets it exactly when it would stop verifying anyway;
  2. sets the cookie (Part 3).
Without Remember Me there is no cookie and no Redis key. You hold only a five-minute access token in page memory. Reload the page, or wait five minutes, and the session is gone. Lesson 4 shows what the web app does at that moment.

Part 3 · The cookie

setRefreshCookie: 

res.cookie(`${API_COOKIE_NAME}_rf`, this.aesEncrypt(refreshToken), {
  expires: new Date(exp * 1000),         // the token's own exp (since #116; was maxAge: 30 days)
  httpOnly: true,
  sameSite: production ? 'none' : 'lax',
  secure: production,
});

Each attribute is a defence. MDN, for the browser's side of each:

  • httpOnly: “forbids JavaScript from accessing the cookie”, which “mitigates attacks against cross-site scripting.” The web app's own code cannot read it, so neither can a script injected into the page. [MDN]
  • secure (production): sent “only when a request is made with the https: scheme (except on localhost).”
  • sameSite: lax locally; none in production, where the web app and API may sit on different sites. MDN: with None “the Secure attribute must also be set”, which is why the two flip together.
  • expires: the moment the browser deletes the cookie. It is the refresh token's exp, the same moment its Redis key expires: one lifetime, three places.
Which limit wins? (Fixed in #116.) The cookie used to have its own maxAge of 30 days while the token inside was signed for 6 months. The browser deleted the cookie first, so honest users got 30 days, but a cookie value copied by an attacker is not bound by your browser's maxAge: the server accepted it for the full 6 months. Now there is one lifetime: the cookie, the token and its Redis key expire together, at the earlier of 30 days after the last refresh (idle timeout) and 90 days after you signed in (absolute timeout). The token carries the sign-in time as auth_time (OpenID Connect Core §2) through every rotation, so refreshing cannot extend a session past that cap. OWASP: an absolute timeout “limits the amount of time an attacker can use a hijacked session.” [OWASP]

Why encrypt a cookie JavaScript cannot read?

aesEncrypt wraps the refresh token in AES-256 with API_ENCRYPTION_KEY before it becomes the cookie value. Lesson 2 showed a JWT's payload is readable by anyone who sees it; encryption means a cookie that leaks into a log or a proxy shows nothing useful. And readCookie treats a value that will not decrypt as no cookie at all.

Part 4 · A refresh, line by line

When the access token expires, the web app calls the refreshToken mutation (lesson 4 covers who calls it, and when). The browser attaches the cookie by itself. SessionService.refresh:

  1. Read the cookie and decrypt it. Missing or undecryptable → INVALID_COOKIES.
  2. Verify the token with API_SECRET_REFRESH. Forged or expired → INVALID_TOKEN.
  3. Load the user: a deleted user cannot refresh.
  4. Delete its Redis key, atomically: const used = await this.store.del(key). Redis returns how many keys it removed, so only the first request with this token ever sees 1.
  5. used is 1 → rotate: mint a new access token and a new refresh token, store the new one, set the new cookie.
  6. used is 0 → reuse: this token was already spent. Delete every refreshToken:<userId>:* key and fail with INVALID_TOKEN.

Step 5 is rotation, as the OAuth security guidance recommends: “the authorization server issues a new refresh token with every access token refresh response”, and the old one is invalidated. [RFC 9700 §4.14.2] Every refresh token works exactly once.

Part 5 · Reuse detection: catching a stolen cookie

Suppose an attacker copies your cookie. Now two parties hold the same refresh token, and only one can spend it. Whoever presents it second finds its key already gone. The server cannot tell who is who: RFC 9700 notes that it “cannot determine which party submitted the invalid refresh token”, so it revokes the active one. TravelBliss goes further and deletes all of that user's refresh tokens, ending every remembered session, the attacker's included.

Predict, then play

For each scenario, decide what the last click does before making it. Use Reset between scenarios.

  1. Sign in · refresh · refresh.
  2. Sign in · attacker steals · attacker refreshes · you refresh.
  3. …continue scenario 2: attacker refreshes again.
  4. Sign in · attacker steals · you refresh · attacker refreshes.
  5. Sign in · attacker steals · you sign out · attacker refreshes.

The simulator runs the same rules as session.service.ts (its source), minus expiry and signatures.

Compare scenarios 2 and 4: the order only changes who sees the error first. Either way the second refresh trips the alarm and every remembered session ends, yours included: rotation cannot tell the thief from you, so it stops both.

Part 6 · Signing out, briefly

SessionService.end undoes all of the above: it puts the access token on a Redis blacklist until its exp (that is why, in lesson 1, a signed-out token made you a guest), deletes the refresh token's key, and clears the cookie. Lesson 4 picks this up, including a weakness in how that blacklist is keyed.
