Lesson 4 · about 30 minutes · web side

The web side, sign-out, and three gaps

Lessons 1–3 were the API. This one is the browser: how the web app attaches the token, refreshes it without you noticing, survives a reload, and signs out. It ends with three real gaps in this code, which you will trigger yourself.

Warm-up, from memory

1. You signed in without Remember Me and reload the page.
2. An attacker spends your stolen refresh cookie first; then you refresh.

Part 1 · Two things the browser holds

Where Survives a reload?
Access token a plain variable in session/link.ts no
Refresh token the travelBliss_rf HttpOnly cookie (lesson 3) yes, 30 days

The access token is never written to localStorage or a cookie. A reload loses it on purpose and gets a new one through the refresh cookie (Part 3). Everything else in the app sees only useSession(): 

const { user, signIn, signOut, isSigningIn } = useSession();

Part 2 · Every request: attach, and on failure refresh once

Apollo Client sends each GraphQL operation through a chain of links that “execute in sequence”; each can change the operation and pass it on with forward(operation). [Apollo docs] TravelBliss's chain, in App.tsx: 

link: from([createSessionLink(uri), errorLink, httpLink])

createSessionLink is two links in one:

  1. Attach (L40): if there is an access token, add Authorization: Bearer ….
  2. Retry (L44): if the response has an UNAUTHENTICATED error, call refreshToken, store the new access token, and send the original operation again with it. Three guards keep this from looping:
    • only UNAUTHENTICATED triggers it (remember this for Gap C);
    • the RefreshToken operation itself is never retried;
    • each operation retries once, marked retried; a second failure reaches the page.

One more detail. If five queries fail together, they must not send five refreshes: with rotation, the second would be reuse and revoke everything (lesson 3). So the refresh request is shared: 

let pending: Promise<string | null> | null = null;
const refresh = () => (pending ??= fetch(… RefreshToken …) … .finally(() => { pending = null; }));

The first failure starts the request; the other four wait on the same promise. [L20–38] Keep in mind where that variable lives: in this page's JavaScript.

Part 3 · A reload, and why it no longer flashes

On reload the access-token variable is null. Follow the request that rebuilds the session:

  1. SessionProvider runs the GetMe query with no Bearer header.
  2. me is @Authorized(), the caller is a guest → UNAUTHENTICATED (lesson 1).
  3. The retry link calls refreshToken; the browser attaches the cookie → new access token (lesson 3).
  4. GetMe is retried with the new token → the user.

Until step 4 finishes, SessionProvider renders only a full-screen loader, so no part of the app can show signed-out UI to a signed-in user. Then the route guards decide:

  • ProtectedRoute: no user → Navigate to /sign-in, remembering where you were (state.from).
  • PublicRoute: a user on /sign-in → Navigate back to state.from, or home.
The flash you saw. Earlier, the provider copied the query result into state with useEffect. For one render the query was done but user was still empty; the guard redirected to sign-in in that gap, and the header (outside the guards) showed “Sign In”. The fix was two rules now in CODING_STANDARDS.md: derive, don't copy (user is computed from the query in render), and hold everything behind the loader until the first check settles.

Part 4 · Signing out

signOut() calls the logout mutation, then forgets the token locally: 

await logout();            // server side, below
setAccessToken(null);      // drop the in-memory token
setIsSignedOut(true);      // hide the cached user: the query still holds it

On the API, SessionService.end does three things: blacklists the access token in Redis until its exp, deletes this device's refresh key, and clears the cookie. That server-side part is the point. OWASP: logout “must invalidate the session at least on server side”, because “deleting a cookie alone does not invalidate a stolen copy.” [OWASP Session Management]

A hardening note on the blacklist

The blacklist key is the raw token string: blacklist:<token>. OWASP's JWT cheat sheet warns that keying a denylist on the raw token is unsafe because JWTs are malleable: one token can sometimes be re-spelled as a different string that still verifies. [OWASP JWT] I tested the classic trick against our library: the last character of an HS256 signature carries two unused bits, so four spellings decode to the same bytes. jsonwebtoken rejected all three re-spellings with invalid signature, because it compares the signature as a string. So it is not exploitable here today; keying on a claim inside the token (a unique jti) would make that independent of the library's internals.

Part 5 · Three gaps

Each gap below is real in this code. Trigger it in the simulator, answer the prediction, then write down your own fix before opening the nudge. We will design the real fixes together afterwards.

Gap A · Signing out one device, or changing your password, ends nothing else

Try: laptop and phone both sign in; laptop signs out. Then: both sign in, attacker steals the laptop's cookie, laptop changes password, attacker refreshes.

After the laptop changes its password, can the attacker still refresh?

OWASP says sessions should be renewed after any privilege change, password changes included, and recommends letting users “remotely terminate sessions manually.” [OWASP] changePassword does neither.

A nudge (after you have written your fix)

Lesson 3 already contains a line that ends every remembered session of a user. Where is it, and what else would you need so the current device stays signed in, and so access tokens already out there stop working too?

Gap B · Two tabs refresh at once, and everyone is signed out

Try: laptop signs in; then “two tabs refresh at once”. Watch Redis.

A nudge

Gap C · An admin with an expired token sees “not allowed”
