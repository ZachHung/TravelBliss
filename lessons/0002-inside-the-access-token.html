Inside the access token

Lesson 1 treated the access token as a sealed pass. Today you open it: read what it says, and see why the API can trust a string the browser hands it.

Warm-up, from memory

A new mutation is added: @Authorized(Role.ADMIN) deleteUser. A guest calls it. What comes back?

Three parts, separated by dots

The access token is a JWT (JSON Web Token): “a compact, URL-safe means of representing claims”, written as “a sequence of URL-safe parts separated by period ('.') characters.” [RFC 7519 §3] 

header.payload.signature
  • Header: which algorithm signed it.
  • Payload: the claims, facts about the bearer.
  • Signature: proof the first two parts came from the API, unchanged.

The header and payload are only encoded (base64url), not encrypted. OWASP is blunt: “anyone who obtains the token can read every claim.” [OWASP JWT Cheat Sheet]

Where those claims come from

At sign-in, createTokens makes the token: 

sign({ userId }, getEnv('API_SECRET_JWT'), {
  expiresIn: getEnv('API_JWT_EXPIRED'),   // "5minutes" in .env.example
});

We only put userId in. The library adds iat (issued at) automatically, turns expiresIn into exp, and signs with HS256 by default. [jsonwebtoken] Both times are seconds since 1970. [RFC 7519 §2]

Since the payload is readable, it carries only an id. Never a password, and nothing you would mind a stranger seeing.

Why the API trusts it

The signature is a keyed hash (HMAC) of the header and payload, computed with API_SECRET_JWT, a secret only the API holds. On every request, verifyToken calls verify, which recomputes the signature and checks exp. These are the library's real answers for our sample token:

Try verify says
the token as issued valid: returns the payload
change userId in the payload, keep the signature JsonWebTokenError: invalid signature
verify with a different secret JsonWebTokenError: invalid signature
a token past its exp TokenExpiredError: jwt expired

verifyToken catches every one of these and returns undefined, and from lesson 1 you know what that makes the caller: a guest.

Reading needs nothing. Writing a token the API accepts needs the secret. That asymmetry is the whole trick: the inspector above can decode, but it can never tell you whether a signature is genuine.
