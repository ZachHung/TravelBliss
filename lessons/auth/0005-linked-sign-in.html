Signing in with Google and Facebook

A linked sign-in lets someone sign in through Google or Facebook instead of a password. You will follow one round trip from the button to the signed-in page, learn the three checks that stop a forged trip, and predict, for any situation, which user the API signs in as.

Warm-up, from memory

1. A page loads with a valid travelBliss_rf cookie and no access token.
2. You add a day to the exp claim of your own access token.

Part 1 · Five new words

Google and Facebook play the same role here: a provider, a site that already knows who the person is and will tell TravelBliss, if the person agrees. The protocol for that is OAuth 2.0's authorization code grant. [RFC 6749 §4.1]

Word What it is here
Authorization code A one-time ticket the provider puts in the URL when it sends the browser back. Worth nothing alone: only the API, with its client secret, can trade it for the person's profile.
Callback The API page the provider sends the browser back to: GET /auth/google/callback?code=…&state=…
State A random value the API makes at the start, which comes back unchanged in the callback. Proves the callback belongs to a trip this browser started.
PKCE “Pixy”. A secret (the code verifier) the API keeps, whose hash goes to the provider at the start; trading the code requires the secret itself. [RFC 7636 §4.2]
Provider user id The provider's permanent id for the person (Google calls it sub). The only thing a linked sign-in is matched on.

  1. Button. The sign-in page shows one button per provider the API offers (query linkedSignInProviders). A click runs the startLinkedSignIn mutation, then sends the whole page to the URL it returns: window.location.assign(…). [LinkedSignIn.tsx]
  2. Start. LinkedSignInService.start makes a state and a code verifier, saves the flow { provider, codeVerifier, userId? } in Redis as linkedSignInFlow:<state> for 10 minutes, sets the travelBliss_ls cookie to sign-in:<state> (HttpOnly, only sent to /auth), and returns Google's consent URL.
  3. Google. The person signs in to Google and agrees. Google redirects the browser to the callback with code and the same state. TravelBliss code runs nowhere during this step.
  4. Callback. The Express route /auth/:provider/callback hands code and state to finish, which runs the three checks (Part 3), trades the code for a profile, finds the user (Part 4), and calls SessionService.start(userId, { remember: true }): the same function password sign-in uses, so it sets the same rf cookie (lesson 3).
  5. Back to the web app. The route answers with a redirect to /. That is a fresh page load with an rf cookie and no access token: your warm-up question 1. SessionProvider refreshes, and you are signed in.
Why a mutation, not a plain link? A link like <a href="/auth/google"> would be simpler, but when you connect Google from the account page (Part 5), the API must know who you are. Your access token lives in a JavaScript variable (lesson 4), and a page navigation never carries it. A GraphQL mutation does, through the session link. So startLinkedSignIn reads auth?.user.id: set means connect, unset means sign in. [resolver]

Part 3 · Three checks on the callback

The callback is a public URL; anyone can open it with any code and state. finish refuses a trip unless all three hold:

1. The state matches this browser's cookie

state === started.state, where started comes from the travelBliss_ls cookie. Without this, an attacker could start a trip, sign in to their own Google account, and stop just before the callback. They send you that callback link. You open it while signed in, and their Google account is now connected to your TravelBliss user: they can sign in as you. RFC 6749 calls this CSRF against the callback, which “allows an attacker to inject its own authorization code”, and asks for a value that “binds the request to the user-agent's authenticated state”. [RFC 6749 §10.12] The cookie is that value: your browser never received the attacker's cookie.

2. The flow exists, once

consumeFlow reads the flow with Redis GETDEL: get and delete in one step, so a second use of the same callback finds nothing. The 10-minute expiry makes a leaked state useless soon after. [L177] You saw the same delete-to-claim move in lesson 3's refresh rotation.

3. The code is traded with the verifier

Google only hands over the profile if the API sends the code and the code verifier whose hash it saw at the start. A stolen code alone is worthless. PKCE was designed against that “authorization code interception attack” [RFC 7636], and today's OAuth security advice recommends it even for server apps like ours. [RFC 9700 §2.1.1] Facebook's flow here ignores the verifier; checks 1 and 2 still bind it.

Every failure becomes a redirect, never a crash: finish catches everything and sends the browser to /sign-in?error=<code> (or /account?error=… when connecting).

Lesson 2 asked: why trust a token? Because of its signature. Google's profile arrives as a signed JWT too (an ID token), yet google.ts only decodes it. That is allowed when the API received it directly from Google's token endpoint over HTTPS: the TLS connection already proves who sent it. [OIDC Core §3.1.3.7] A signature matters when a token passes through hands you don't trust. This one never did.

Part 4 · Which user is this?

Google has said “this is sub 1081…, email ann@mail.test”. userFor asks, in this order:

  1. Is there a linked_sign_in row for (Google, this sub)? Then that row's user, full stop. Connecting a sub that belongs to someone else fails with LINKED_SIGN_IN_TAKEN. The table is unique on (provider, providerUserId), so one Google account links to at most one user.
  2. Connecting? Insert a row for the signed-in user.
  3. Does a user already have this email? Then fail with EMAIL_TAKEN_SIGN_IN_TO_LINK: sign in with your password, then connect.
  4. Otherwise create a user without a password, and its row, in one transaction.

Two rules hide in that order. Match on the sub, not the email: OpenID Connect says sub and the issuer “are the only Claims that an RP can rely upon as a stable identifier”, and email “MUST NOT be used” as one. [OIDC Core §5.7] People change emails; the sub never changes. Never link by email: TravelBliss registration does not check that you own the email you type. If Mallory registers with Ann's address first, and Ann's Google sign-in then joined that account automatically, Mallory would hold a working password to Ann's account. So step 3 refuses instead. [ADR 0005]

Try it: predict, then run

Ann has a password account with ann@mail.test; Bob is another user. Set a situation, choose your prediction, then run it. Try at least these four: a first Google sign-in with a new email; the same with Ann's email; the callback opened in another browser while connecting; Ann connects a Google account that is linked to Bob.

Part 5 · Landing, errors, and the account page

  • Errors come back as ?error=<ErrorCode>. LinkedSignInAlert turns the code into a sentence and clears it from the URL when dismissed.
  • Connect is the same round trip started while signed in: the flow stores userId, the cookie says connect:, no new session is started, and the browser returns to /account.
  • Disconnect (disconnectLinkedSignIn, @Authorized()) refuses with LAST_SIGN_IN_METHOD if it would leave a user with no password and no linked sign-in, a user nobody could ever sign in as. It locks the user's row first, so two disconnects at once cannot both pass the count. [L148]
  • Set password (setPassword) gives a provider-only user a password, after which disconnecting is allowed.
  • Nullable fields. A user created by Google may have no password, email, phone or birthday. Any code that reads them must handle null.

Practice

1. An attacker sends you a callback link from a trip they started. You open it.
2. Signing in, Google's sub is linked to Bob, but the email is Ann's.
3. Why not join a Google sign-in to the user with the same email?
4. The callback request is sent twice with the same code and state.
5. How does the web app get an access token after a Google sign-in?
6. Why is the trip started by a mutation rather than a link?
7. A user with no password disconnects their only linked sign-in. Which error code?
