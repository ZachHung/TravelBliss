Lesson 1 · about 10 minutes

Who are you, and what may you do?

Every request to the TravelBliss API is asked two questions, in order. By the end of this lesson you will predict, for any request, which question stops it and what error comes back.

Two questions, two names

Authentication answers who are you? Authorization answers what may you do? OWASP puts it in one line: authorization is “the process of verifying that a requested action or service is approved for a specific entity”, and it is “distinct from authentication which is the process of verifying an entity's identity.” [OWASP]

The order matters: you cannot decide what someone may do until you know who they are. Someone the API cannot identify is a guest.

How a request says who it is

After signing in, the web app holds an access token, a long string the API issued. It sends that token with every request in one HTTP header: 

Authorization: Bearer eyJhbGciOiJIUzI1NiIs…

“Bearer” is a standard scheme. Its defining property: “any party in possession of the token” can use it “in any way that any other party in possession of it can.” [RFC 6750 §1.2] Whoever holds the token is you, as far as the API knows. That is why the web app keeps it in memory only; lesson 3 covers why.

What is inside the token, and how the API knows it was not forged, is lesson 2. For now it is a sealed pass.

The pipeline: one request, three stops

1 · AuthenticateTurn the header into a signed-in user, or nobody.
→
2 · AuthorizeDoes this field allow this caller?
→
3 · ResolveRun the code and return data.

Stop 1: authenticate, once per request

Before any GraphQL field runs, the API builds the request's context by calling SessionService.authenticate with the header. It returns a user or undefined:

  • no header, or not Bearer … → guest
  • token forged or expired → guest
  • token on the logout blacklist → guest
  • user since deleted → guest
  • otherwise → ctx.auth = { user, token, exp }

Being a guest is not an error yet. Some fields are open to everyone: login and register have to be, or nobody could ever sign in.

Stop 2: authorize, per field

Protected fields carry a decorator. In user.resolver.ts: 

@Authorized()            // any signed-in user
public me(…)

@Authorized(Role.ADMIN)  // signed-in AND role ADMIN
public async allUser(…)

For each decorated field, type-graphql calls our authChecker with the roles the decorator lists [type-graphql docs]: 

!!auth && (roles.length === 0 || roles.includes(auth.user.role))

Read it aloud: someone is signed in, and either no role is required or they hold one of the roles.

Which error comes back

When the checker says no, type-graphql picks the error by one thing only: did the decorator list roles? From its source: 

throw roles.length === 0 ? new AuthenticationError() : new AuthorizationError();
Decorator Checker says no → Meaning
@Authorized() UNAUTHENTICATED We don't know who you are.
@Authorized(Role.ADMIN) UNAUTHORIZED You may not do this.
The surprise: a guest calling allUser gets UNAUTHORIZED, not UNAUTHENTICATED, because the decorator lists a role. The error describes the field's rule, not the caller.
Plain HTTP has the same split: 401 for missing or invalid credentials, 403 for valid but insufficient ones. [MDN] GraphQL returns HTTP 200 and puts the code in errors[].extensions.code instead.

Practice: predict the outcome

Answer from memory first, then check the table only if stuck.

1. SessionService.authenticate answers which question?
2. A guest queries me.
3. A signed-in user with role USER queries allUser.
4. A guest queries allUser.
5. A signed-in user with role USER queries me.
6. A user signs out, then sends the same token again to query me.
7. A guest calls the login mutation with the right password.

Try it on the real API

With pnpm dev:local running, see questions 2 and 4 for yourself:

curl -s localhost:8000/ -H 'content-type: application/json' \
  -d '{"query":"{ me { username } }"}'

curl -s localhost:8000/ -H 'content-type: application/json' \
  -d '{"query":"{ allUser { id } }"}'

Look for "code" in each response, then stop the servers with pnpm dev:stop.
